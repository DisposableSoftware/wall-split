## Implementation notes

- `GtkDropTarget` with `Gdk.FileList` and `Gdk.DragAction.COPY`, on the stack that holds the hint and the preview.
- The cut position `cut_x` in source pixels is the single source of truth in `app.py`. The dropdown and slider both write it.
- `WIN-7` widens the cut range of the original `AGENTS.md` (`[0, W]`) to `[1, W−1]`: a zero-width output can't be saved.
- The rejection cue is an inset `outline` on the stack, not a `box-shadow`: GTK draws the outline over the children, so the preview can't hide it.
- Whether a file is an image is left to GdkPixbuf, which picks its loader from the file's leading bytes. `Gio.content_type_guess` on the data needs the shared-mime-info database, which the Nix build sandbox doesn't have.
- The drop target accepts both copy and move (`WIN-3`). On Wayland, GTK takes a drop's actions from the compositor's chosen action once it is non-zero (`gdk/wayland/gdkdrop-wayland.c`, `gdk_wayland_drop_update_actions`), and a target whose actions don't overlap refuses the drop (`gtk/gtkdroptarget.c`, `gtk_drop_target_accept`). Hyprland chooses move for a file manager's copy-or-move drag before the target has answered, so a copy-only target never sees the drop. wlroots, and so the headless sway runner, sends no action at that point, which is why the headless checks didn't catch it. GTK's default handlers still prefer copy when both are on offer; a move needs nothing from the app, since GTK never deletes a dragged file itself.
